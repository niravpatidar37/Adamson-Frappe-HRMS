# Design: Applicant screening funnel — knockout questions before AI ranking

Generated by /office-hours on 2026-09-28
Branch: main
Repo: Adamson Frappe HRMS
Status: APPROVED
Mode: Startup (intrapreneurship)

## Problem Statement

Adamson receives around 1,000 applications per opening, including for assembler
roles. Recruiters cannot read them all. They need a ranked shortlist to work
through from the top, not a system that rejects people on their behalf.

## Demand Evidence

- A recruiter asked for this directly. In their framing: "tell me who to look at first."
- Volume, in the user's words: "we receive 1000 applications even for assembler job
  its hard to review all of them."
- Not yet captured: the recruiter's name and role, hours spent per shortlist today,
  and how many openings per month hit this volume. The Assignment below collects them.

## Status Quo

Reviewing every application by hand does not scale to 1,000 per opening. The exact
current workflow (full reading, skimming, or a keyword filter) has not been observed
first-hand yet.

## Target User & Narrowest Wedge

- **User:** the Adamson recruiter who owns high-volume openings. The role mix is
  hourly shop-floor roles (assembler, operator) plus skilled and office roles.
  The hourly roles drive the volume.
- **Wedge:** one assembler opening, screened end to end through the funnel below,
  producing a ranked list the recruiter works from the top.

## Constraints

- Everything runs on Adamson's own server. Frappe never sees the parsed profile
  (README, ADR 0001).
- No auto-rejection by AI. A score influences a hiring decision.
- Nothing is enabled until callback signature verification exists (README).
- Criterion text must pass the `reject_disallowed_features` guard in `job_blueprint.py`.

## Premises (agreed)

1. The problem is ordering, not rejecting. At 1,000 applications per opening, the
   recruiter needs a ranked shortlist to work through from the top. The AI never
   auto-rejects.
2. For hourly roles, the applicant's own answers beat resume parsing. Shift,
   location, certification, work authorization and start date are asked on the
   application form, not inferred from a PDF.
3. The fix belongs upstream: knockout questions on Frappe's job application form,
   passed to the engine, evaluated by the existing rules engine. A FAIL is allowed
   only when the applicant explicitly declared it, never when information is missing.
4. The LLM ranks only the applicants who pass. The same funnel serves skilled roles,
   where the rules are lighter and the resume carries more of the weight.

## Why the current pipeline doesn't shrink the queue

- `rules_engine.py:119-130` returns `UNKNOWN` (sent to human review) for every
  location, certification and authorization criterion, because "structured
  application fields [are] not present on the parser profile alone."
- `rules_engine.py:107-117`: a skill not found in the resume is `UNKNOWN`.
- `JobBlueprint.other_requirements` (shift patterns, on-call) is never evaluated.
- `tasks.py:40` (bridge): an applicant with no resume attachment is never dispatched.

Result: with 1,000 thin assembler resumes, nearly every applicant comes back
`UNKNOWN`, and the recruiter's queue stays at about 1,000.

## Approaches Considered

- **A: Knockout filters in Frappe only.** Rejected: knockout decisions would bypass
  the audit ledger and the bias guard, and the rules engine would keep returning `UNKNOWN`.
- **C: A separate resume-free path for hourly roles.** Rejected for now: two products
  to maintain, plus plant-side logistics for a skills check. Revisit if hourly
  applicants abandon a form that asks for a resume.

## Recommended Approach: B. Blueprint screening questions, evaluated by the rules engine

> **Superseded for v1** by the engineering review (D8). See "Revised v1 scope" near the
> end of this file. This section now describes the v2 engine path.

1. **Schema:** `JobBlueprint` gains `screening_questions`. Each question has an id,
   text, answer type (yes/no, choice, date), the must-have criterion it answers,
   and the values that pass. Question text goes through `reject_disallowed_features`
   like every other criterion.
2. **Frappe:** the questions for an opening render on that opening's application web
   form. Answers are stored on the Job Applicant.
3. **Bridge:** the signed dispatch carries the answers alongside the resume. For roles
   whose blueprint marks the resume optional, applicants without a resume are still
   dispatched.
4. **Rules engine:** when a criterion has a declared answer, return `PASS` or `FAIL`
   with new reason codes (`DECLARED_MET` / `DECLARED_NOT_MET`), confidence 1.0, and
   evidence `application.answers.<id>`. A missing answer stays `UNKNOWN`, as today.
5. **Queue:** applicants with a declared FAIL are not scored and are listed separately.
   The recruiter confirms them in bulk, so nothing is rejected without a human. PASS
   and UNKNOWN applicants go to LLM scoring and are ranked by qualification tier,
   then match score.
6. **Audit:** the ledger records the answer snapshot next to each rule result, so
   "why was I screened out?" has an answer grounded in the applicant's own words.

Reuses: `rules_engine.py`, `JobBlueprint` and its bias guard, signed dispatch, the
audit ledger, and the existing unit and integration suites.

## Open Questions

- Which 4 to 6 knockout questions does the recruiter actually use for assemblers?
  This comes from the recruiter, not from us.
- How to render per-opening questions on Frappe HR's Job Applicant web form: a child
  table on Job Opening plus web-form script, or something else? This needs a spike.
- Does a declared-fail list confirmed in bulk meet Adamson's legal and HR policy, or
  must each one be reviewed individually?
- What share of hourly applicants apply without a resume today?
- Which languages do applicants use? This affects question wording and LLM ranking.
- Spike questions 4 and 5 (`docs/phase-0-spike.md`) are still open.
- The README "Status" section predates commit 86c704c and needs updating.

## Success Criteria

On one real assembler opening:
- At least 60% of applicants resolve to a deterministic PASS or FAIL rather than UNKNOWN.
- The recruiter produces a shortlist from the top 50 ranked applicants, and their
  time per shortlist is measurably lower than today's baseline. The baseline is
  measured in the Assignment.
- Zero rejections without a human confirming them.
- The application completion rate drops by less than 10% after adding the questions.
- Each knockout question passes a 4/5ths-rule adverse-impact check on its outcomes.

## Dependencies

- Callback signature verification (launch blocker).
- Spike questions 4 and 5.
- Recruiter time to define knockout questions and check the ranked list.

## The Assignment

Sit with the recruiter who asked for this for one hour, on one real assembler opening.
1. Ask them to write down the 4 to 6 questions they would ask every applicant before
   reading a resume.
2. Time them screening 50 real applications the way they do it today.

Bring back both: the questions become the first `screening_questions`, and the time
becomes the baseline for the success criteria.

## What I noticed about how you think

- The session turned when you said "we receive 1000 applications even for assembler
  job." Until then the answers were labels. That one number reshaped the whole design.
- You asked to "help me to find the best strategy to screen applicants," not for a
  better model. That instinct was right: the biggest win here is a form field, not a
  prompt.
- You accepted the recommended option at almost every step. That's fine when you
  agree, but next time say where you'd push back. Your knowledge of Adamson's
  applicants is the one input this design can't get from the code.

## Revised v1 scope (after D8)

v1 lives in Frappe only. There are no engine, bridge-dispatch or migration changes.

1. Job Opening custom fields hold the vetted knockout requirements (R4): required
   shift pattern, work site, required certification name, start-by date, and whether
   legal authorization to work is required. Each is optional per opening.
2. Job Applicant custom fields hold the applicant's yes/no answers to the same five
   types, shown on the application web form only when the opening sets that requirement.
3. A read-only "Knockout Result" field on Job Applicant: Declared ineligible (any
   required answer is No), Unanswered (any required answer missing), or Eligible.
   This is set in a small, tested server-side function on save, the only new logic.
4. A saved list view per opening: Eligible first, then Unanswered, then by creation.
   Declared-ineligible applicants appear in a separate filter for the recruiter to
   confirm. Nothing is rejected automatically.
5. ADR 0001 amendment note: v1 knockout filtering is Frappe-side, from
   applicant-declared fields. The engine's ledger takes over when the v2 scorer lands.
6. Covers applicants without a resume too (D1 is moot for v1).

Deferred to v2, with the scorer: the engine evaluation path, the signed blueprint
snapshot, R3 (dedup key), R5 (re-screen button), R6 (answers-first parse), the
OV1 callback, and the OV4/OV9/OV10 fixes.

Correction adopted from OV3 (a factual metric fix; no behavior change): the success
criterion ">=60% resolve to deterministic PASS/FAIL" is replaced by "declared-ineligible
share per opening, and Eligible-tier size versus recruiter review capacity."

v1 tests (required proof):
- Unit: knockout result function. All Yes gives Eligible; any No gives Declared
  ineligible; any missing gives Unanswered; a requirement not set on the opening is ignored.
- Fixture: new custom fields exist and the web form shows only the questions the
  opening requires.
- Manual QA: the recruiter list sorts Eligible, then Unanswered; declared-ineligible
  applicants appear only in their filter; no status changes to Rejected automatically.
